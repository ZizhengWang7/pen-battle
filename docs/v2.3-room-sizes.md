# V2.3: rooms for 2–4 players

Hosts choose 2, 3 or 4 players before creating a room; the default remains 4. The server validates `maxPlayers`, includes it in public room state, and fixes the slot array to that capacity. No event can change capacity after creation. Older clients that omit it create four-player rooms; explicit invalid values are rejected.

The lobby shows occupied slots, readiness and the immutable capacity. Starting requires exactly that many connected, ready participants and a host request. Missing players' slots remain reserved during reconnect grace. Credential digests remain private, invitation links still contain only room codes, and expired credentials are rejected even before the next cleanup sweep.

Online matches create only the actual participants. Both modes shuffle their initial turn order using the server's match seed. Two pens face off on opposite sides; three use an equilateral triangle around the table center. The four-player layout and four-player local games are preserved. Collision shapes, impulse calculations, friction, damping, hand animation and pen classes are unchanged.

Classic skips eliminated participants and ends at one survivor. Evolution scores each victim once, respawns until five points, and preserves self-fall downgrades without removing historical points. Rematches preserve capacity and reset the match state. Scoreboards render only participants, including a full-width third card on narrow screens.

## Repeatable checks

```sh
npm test
npm run build
```

Local release verification passed: 73 unit/regression groups, 19 Socket.IO integration groups, both production builds, and the complete 375 px browser/gameplay smoke at 2, 3 and 4 players. New deterministic fixtures cover safe spawns, shuffled participant-only turns, full-room rejection, readiness/host gates, fixed capacity, shakes, Classic winners and skipped eliminations, Evolution scoring/upgrade/respawn/five-point wins, self downgrade, rematches, guest/host reconnection, reserved slots, credential expiry and host migration at all three capacities. Deterministic elimination fixtures manipulate bodies only inside local tests, never production.

For browser checks, start the built local server in one terminal:

```sh
PORT=17321 HOST=127.0.0.1 FRONTEND_ORIGINS=http://127.0.0.1:17321 npm run server
```

Then run sequentially in another terminal, using installed Chrome:

```sh
SMOKE_PLAYERS=2 npm run test:browser -- --gameplay
SMOKE_PLAYERS=3 npm run test:browser -- --gameplay
SMOKE_PLAYERS=4 npm run test:browser -- --gameplay
```

Each check creates isolated browser contexts at 375 px, selects capacity, joins by invitation, removes/rejoins a guest, readies/starts, flicks through trusted touch events, shakes, refreshes a participant, and checks visible agreement and browser/asset errors. It also checks local Classic/Evolution remain available. Online and local gestures use Chrome touch emulation to avoid inconsistent headless mouse capture. A timer-backed presentation clock avoids macOS headless display-link stalls; simulation and networking use real time.

`--gameplay` reclaims the same smoke room using credentials kept only in memory. It checks secure WebSockets, unauthorized and wrong-room rejection, duplicate action rejection, real outward flick eliminations and a Classic winner, a rematch at the same capacity, then Evolution falling/respawning without ending the match, synchronized state and a one-turn shake. It sends legal client actions only. It is a small functional check, not a load benchmark.

## Public rollout

The existing Render service automatically deploys `main`. No service, hosting plan or production configuration changes are required. After pushing, compare `/releases/v2.3.json` and the homepage asset hashes with the built files, verify HTTPS and `/health`, then repeat the three smoke commands with `SMOKE_URL=https://pen-battle.onrender.com`. Reusing each browser room for protocol checks bounds room creation to three rooms. The final release report records the actual post-push observations; local test results alone do not prove a production rollout.

Private Render logs/settings require dashboard access and are separate from public health and functional verification. Physical phones and WeChat remain outside the Chrome emulation check. The public smoke does not attempt an Evolution five-point finale; that behavior has deterministic unit and local Socket.IO coverage. In-memory state and Free-hosting cold starts remain the limitations documented in the README.
